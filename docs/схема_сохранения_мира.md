# Схема: сохранение и загрузка всего мира (точное продолжение)

Цель: файл `.gpworld`, после загрузки которого симуляция идёт **бит в бит** как без сохранения
(при той же версии кода и тех же параметрах). Это проект, кода пока нет.

Уже есть **приблизительное** сохранение, его не трогаем: `GenePool.getPoolData / setPoolData` (GenePool.ts:4617 / 3170),
`src/ui/saveLoad.ts`, `src/devResume.ts`. Оно хранит гены, позиции, возраст и энергию и пересоздаёт свимботов заново,
поэтому мозг, память, болезни, части тела, ГСЧ и долги теряются. Остаётся как «мягкая загрузка» для файлов другой версии.

---

## 0. Главное препятствие: глобальный ГСЧ нельзя сохранить

`gpRandom()` (Globals.ts) в браузере просто вызывает `Math.random()`: его состояние недоступно, зерна нет.
В headless `Math.random` подменён замыканием mulberry32 (tools/headless.cjs:37), но состояние `a` тоже спрятано.

**Первый шаг:** заменить `gpRandom` на свой mulberry32 с видимым состоянием:
```ts
export const rngState = new Uint32Array( 1 );            // Globals.ts
export function setRandomSeed( seed: number ) { rngState[0] = seed >>> 0; }
export function gpRandom(): number { /* тот же mulberry32, что в headless.cjs и DecisionKernel.botRandom */ }
```
- Браузер: зерно при старте берётся из `crypto.getRandomValues` и пишется в заголовок файла и в `runs/.../meta.json`.
- headless: `createSimulation(seed)` вызывает `setRandomSeed(seed)`. Алгоритм и зерно те же, поэтому старые прогоны
  с тем же `--seed` дадут тот же результат. Это надо проверить: `form-census --seed 1 --steps 3000` до и после правки,
  CSV должны совпасть. Подмену `Math.random` в песочнице оставить: она нужна для двух прямых вызовов `Math.random`
  в тестовой функции GenePool.ts:4956/4962.
- Рисование (`_marks`, GenePool.ts:2053) и дальше берёт `Math.random`. После правки оно перестаёт сдвигать
  ГСЧ симуляции, и это хорошо.

У каждого свимбота есть свой ГСЧ: `SharedState.random` (Uint32, DecisionKernel.ts:52). Он сохраняется вместе с остальными массивами.

## 1. Перечень состояния

Обозначения: **С** — сохранять, **П** — пересчитать при загрузке, **Н** — не сохранять (и почему).

### 1.1 Общая память `SharedState` (SharedState.ts), строка на слот `s`
Все массивы сохраняются **как есть, двоичной копией**. Для свимботов берётся префикс `[0, hwS)`, для еды префикс `[0, hwF)`.
`hwS` — «верхняя отметка»: 1 + наибольший слот, который хоть раз был занят (ищем по `st.bots`/`_swimbots[s].getIndex()`).
Так сохраняются и давно мёртвые слоты: на них могут указывать старые ссылки (`M_PREY`, `seen[]`).

| Массив | Что | |
|---|---|---|

## 2. Формат файла `.gpworld`

Файл целиком сжат gzip: в браузере `CompressionStream("gzip")`, в node `zlib.gzipSync`. Это один и тот же стандарт.
Внутри (до сжатия), little-endian:
```
"GPWORLD\0"            8 байт, магия
u32  headerBytes       длина JSON-заголовка
JSON-заголовок         UTF-8 (держать ASCII), дополнен пробелами до кратного 8
чанки                  подряд, каждый с границы 8 байт (можно делать Float64Array прямо на буфере)
```
Заголовок:
```json
{ "format": 1, "code": "2a88b9d", "codeDirty": false, "created": "2026-10-21T10:00:00Z",
  "littleEndian": true, "worldScale": 2, "seed": 123456,
  "layout": { "MAX_SWIMBOTS":6000, "MAX_FOODBITS":16000, "MAX_PARTS":16, "PS":14, "BOT_STRIDE":37,
              "MIND_STRIDE":88, "NUM_INPUTS":28, "NUM_HIDDEN":6, "NUM_OUTPUTS":12, "BRAIN_SIZE":612,
              "NUM_GENES":256, "MAX_SEEN":20, "FIELD_SIZE":256, "PLANT_COLUMNS":64, "PLANT_ROWS":64,
              "KEY_SIZE":7, "NUM_IMMUNE_MEMORY":3 },
  "clock": 123000, "hwS": 5200, "hwF": 16000, "numAlive": 4100, "startMode": 0,
  "params": { "PLANT_STAGES_ENABLED": false, … },      // только отличия от PARAM_DEFAULTS
  "tweakers": { … }, "counters": { … }, "history": { … },
  "environment": { "active":true, "petri":null, "seeds":[…] }, "gardens":[…], "roots":[…],
  "obstacle": { "x1":…, "y1":…, "x2":…, "y2":…, "enabled":false }, "camera": {…},
  "familyTree": true,
  "chunks": [ { "name":"bots", "type":"f64", "offset":…, "count":… }, … ],
  "hash": { "bots":"9f1c…", … } }                     // хеши чанков, для проверки после загрузки
```
Правила:
- **Всё дробное, от чего зависят шаги, хранить в бинарных чанках.** `JSON.stringify` превращает `NaN` и `Infinity` в `null` и теряет `-0`.
  Скаляры GenePool собрать в чанк `poolScalars` (f64): debts, gardenRadius, currentSpeed, clock, serial, numSick, matingCount, rngState.
  В JSON — только метаданные, целые числа и мелкие списки конечных чисел (roots, gardens, history). Перед записью проверять `Number.isFinite`.
- Чанки свимботов: префиксы общих массивов (`bots`, `parts`, `mind`…); `botSlots` (i32, сохранённые объекты: живые и умершие на прошлом шаге);
  `botGenes` (u8, n×256; при сохранении проверить, что все гены целые 0..255, иначе писать f64); `botBrain` (f32, n×612);
  `botPrivate` (f64, n×12 по §1.2); `botOrigin` (i8, n×16, −1 = нет части); `wasAlive` (u8, hwS).
- Чанки еды: префиксы `food*`, `plant*`, `liveFood`; `foodDecoy` (u8).
- Остальное: `diseaseStrains` (f32, k×7); `envSoil` (f32); `envSoilAt` (i32); `envPlantCount0/1` (i32); `mating*` (f64);
  `famCols` / `famGenes` (если с родословной).

**Размер (оценка, проверить на деле).** На слот свимбота в SharedState около 4,8 КБ (bots 0,3 + parts 1,8 + статика тела 1,2 + mind 0,7 + сеть 0,4 + восприятие 0,4).
У живого добавляется ещё 2,7 КБ (гены и мозг). Слот еды — около 45 Б.
| Свимботов (hwS) | Сырые данные | gzip (ожидание 35–45 %) |
|---|---|---|
| 2000 (2500) | ≈ 17 МБ + еда 0,7 МБ | ≈ 6–8 МБ |
| 8000 (9000) | ≈ 65 МБ + еда 0,7–2,8 МБ | ≈ 22–28 МБ |

Если файл выйдет слишком большим (в порядке выгоды):
1. Хранить из `parts` и статики только первые `numParts` частей. Остальное — мусор от прошлого жильца, он **заведомо не читается**. Это проверить тестом §5.
2. Перед gzip «перетасовать байты» (byte-shuffle) у f64-чанков: сначала все 0-е байты, потом все 1-е и т. д. Обычно это даёт ещё 1,5–2×.
3. Компактный режим: строки только живых и умерших на прошлом шаге, давно мёртвые — нулями. Включать **только если** тест §5 даёт тот же хеш.
4. Родословную не сохранять.

## 3. Порядок сохранения и загрузки

### Сохранение (в `simhost.worker.ts`, новое сообщение `{type:"saveWorld"}`)
1. Обработчик сообщения запускается только между кадрами, а `runFrame` и `runner.task` синхронны. Значит, шаг не может
   быть «посередине» и потоки-помощники спят. Отдельная пауза не нужна.
2. **Синхронно** собрать снимок: `pool.saveWorld()` возвращает `Uint8Array` без сжатия, все массивы **скопированы**.
   Читать только сырые массивы. Нельзя вызывать геттеры с побочными эффектами: `environment.getSoilNutrientAtCell`
   «старит» почву, `syncPartObjects` трогает части.
3. Асинхронно сжать (`CompressionStream`). Симуляция в это время идёт дальше, она работает с другими данными.
4. Отправить странице `postMessage({type:"worldSaved", bytes}, [bytes.buffer])`. Страница делает Blob и скачивание
   `genepool_<дата>_шаг<clock>.gpworld`. Готовый `request` не годится: он не ждёт Promise и не передаёт буфер.

### Загрузка (`{type:"loadWorld", bytes}`, сначала распаковка, потом всё синхронно, за один обработчик)
0. **Проверки.** Магия, `format`, `littleEndian`, `layout`:
   - отличается `worldScale` — ответить странице `{needWorld:N}`. Страница кладёт файл в IndexedDB (как devResume.ts),
     перезагружается с `?world=N` и после старта загружает его;
   - отличается другой ключ `layout` (код поменял раскладку) — точная загрузка невозможна. Предложить
     «мягкую загрузку»: собрать из файла объект для `setPoolData` (гены, мозг, позиции, возраст, энергия, еда, environment, clock);
   - отличается `code` или `codeDirty` — загрузить и предупредить: «продолжит, но не бит в бит».
1. Сбросить время кадров: `_stepDebt = 0`, `_lastFrameTime = 0`, иначе после загрузки будет рывок шагов.
2. **Параметры.** Для каждого `PARAM_LIST` вызвать `setParameter(name, сохранённое ?? значение по умолчанию)`. Помощники подхватят
   при следующей фазе (`syncParams`). Сообщить странице новые значения: окно отладки держит их в localStorage.
   Параметры нужны раньше свимботов: `processPhenotype` читает SIZE_MATURITY_ENABLED, MASS_SCALED_STOMACH_ENABLED и т. п.
3. **Регуляторы** через сеттеры GenePool: `setFoodGrowthDelay, setFoodSpread, setFoodBitEnergy, setHungerThreshold, setAttraction,
   setOffspringEnergyRatio, setMaximumSwimbotAge`, плюс `numFoodTypes`. Сеттеры **перезаписывают энергию всей еды и голод всех свимботов**,
   поэтому они идут до копирования массивов.
4. **Среда:** `environment.setState(...)`, `setTime(clock)`, потом soil, soilAt, plantCount. Затем
   `copyBackgroundTo(_st.background)`, `_environmentImage = makeImage()`, `_pool.setBackgroundImage(...)`.
5. `_clock`, `simClock.step`.
6. **Очистка:** `_foodBits[f].kill()` всем, `_swimbots[s].die()` всем. `die()` увеличивает счётчики и пишет в родословную,
   это потом перезапишется. Затем `_familyTree.reset()`, `Disease.setStrains(...)`.
7. **Объекты свимботов** (для `botSlots`): `genotype.setGenes`, `setBrain`, затем `_swimbots[s].create(s, …, _embryology)`.
   `create` тратит gpRandom, это не страшно (см. шаг 12). Если `botOrigin` отличается от свежего фенотипа, применить
   новый `restorePhenotypeOrder(origin)` и затем `processPhenotype()`. Потом `setPrivateState(...)`.
8. **Объекты еды** (живые по `liveFood`): `initialize(f)` (тоже тратит gpRandom), `setAutotomyDecoy`.
9. **Копирование общих массивов** (`.set()` в **существующие** массивы, буферы не заменять: помощники держат на них ссылки).
   Это перезаписывает всё, что выставили `create/initialize/die`: позиции, флаги `liveSwimbot/alive`, mind, ГСЧ ботов, гены растений, энергию еды.
   Потом для еды вызвать `setColorAccordingToType()`.
10. **GenePool:** `_swimbotWasAlive`, debts, `_serial`, `_roots`, `_gardens`, radius, `_currentSpeed`, mating, `_history`,
    `_numSick`, `_simulationRunning`, `startMode`, obstacle (`setEndpointPositions`, `setEnabled`), камера; `_numSwimbots/_numFoodBits` пересчитать.
    Выбор снять (`setSelectedSwimbot(NULL_INDEX)`), `_viewTracking.reset()`.
11. Родословная (`importState`), затем **`simCounters` целиком** (после `die()`!), затем `writePerceptionParams()`, затем `rebuildAliveIndexCaches()`.
12. **Последним — `rngState`.**
13. Сверка: посчитать хеши чанков снова (`saveWorld()` без сжатия) и сравнить с `header.hash`. Если не совпало, на шаге 7–11
    что-то перезаписали не так: вывести имена расходящихся чанков.
14. Сообщить странице `worldLoaded` и снимок. RunRecorder начинает **новую** папку: добавить колбэк `pool.onWorldLoaded`,
    потому что текущая проверка `step < lastStep` не сработает, если загружен более поздний шаг.

**Параллельные потоки.** Ничего не перезапускать. Их состояние — только общая память и копия параметров. Перед следующей фазой
они сами вызывают `syncParams()`. Важно лишь не заменять `SharedArrayBuffer` (`st.buffers`).

## 4. Подводные камни

1. **ГСЧ** (§0). Без своего `gpRandom` точности нет. `rngState` восстанавливать **после** всех `create()/initialize()/environment` —
   они тратят случайные числа (`Swimbot.create` → личное зерно и `_brain.update()`; `FoodBit.initialize` → позиция и гены растения).
2. **Решение читает старый взгляд.** Порядок шага: DECIDE → PHYSICS → PREPARE_LOOK → LOOK. DECIDE читает `seen*`, `targetPrey*`, `socialX/Y`
   прошлого шага. Значит, это **состояние**, а не кэш.
3. **Отложенные смерти.** Кто умер на шаге N, тот «убирается» (туша, `onSwimbotDied`) в начале шага N+1 по `_swimbotWasAlive`.
   Сохранять `wasAlive` и полный объект таких свимботов: туше нужны позиция, `getDeathCause`, `getPhenotypeMass`, `getGrowthScale`, хищность, возраст.
4. **Номера слотов — это идентичность.** Ссылки M_FOOD/M_MATE/M_PREY/M_NEAR_PRED/M_CALM_PRED/M_NEAREST_SEEN/M_LAST_MEAT, `seen[]`,
   `seenFood`, а также `findLowestDeadSwimbotInArray` / `findLowestDeadFoodBitInArray` («первый свободный слот») зависят от индексов.
   Слоты не перенумеровывать и не «уплотнять».
5. **Два флага жизни.** `st.alive` (`_botAlive`, точный, ставит `notifySwimbotDeathTime`) и `st.liveSwimbot` (флаг объекта).
   `findLowestDeadSwimbot` смотрит оба. Сохранять оба.
6. **Фенотип после автотомии.** `autotomize()` переставляет `_phenotype.parts` (оставшиеся, затем отброшенные), перенумеровывает
   `parent/child`, уменьшает `numParts`. Регенерация (`handleEventsBeforeMoving`, EVENT_REGROW) строит фенотип из генов заново, а
   самопоедание обрезает **навсегда**. Решение: в `Embryology.generatePhenotypeFromGenotype` ставить каждой части `part.origin = p`.
   При сохранении писать `origin` первых `numParts`. При загрузке брать свежий фенотип, выстраивать части по `origin`
   (отброшенные в хвост), `parent → новый номер`, `child → новый номер или NULL_INDEX`, `numParts = origin.length`.
   Сверка: `processPhenotype` должен дать те же `partMass` и `sumPartLengths`, что в файле.
7. **`processPhenotype` и `create` перезаписывают mind/bots** (B_TIMER_DELTA=0, M_COMFORT=−1, тепловая подгонка, `updateBodyParts` двигает части).
   Поэтому копирование общих массивов — **после** создания объектов.
8. **Сеттеры регуляторов трогают всех**: `setFoodBitEnergy` → энергия всей еды, `setHungerThreshold` → M_HUNGER всех. Вызывать их до копирования.
9. **`die()` имеет побочные эффекты** (simCounters, родословная, `_botAlive`), поэтому `simCounters` восстанавливать в самом конце.
10. **Почва «стареет» при чтении** (`ageSoilNutrient` в геттерах Environment). Сохранять сырые `soilNutrient` и `nutrientUpdatedAt`.
11. **`plantCount`** считается в `updateFood`, а читается в следующем шаге через `writePerceptionParams`. Сохранять, не пересчитывать.
12. **Штаммы болезней** — глобальный растущий список. `startSimulation` его не сбрасывает, номера в иммунной памяти ссылаются на него. Сохранять весь.
13. **Гены могут измениться при жизни** (`applyPredatorLevel` переписывает гены хищности, zap, правка). Сохранять текущий генотип, а не родительский.
14. **`_history`** сбрасывается, если последний шаг в нём `>= _clock` (recordHistory). Восстанавливать после `_clock`.
15. **Параметры в headless.** В бандле esbuild нет плагина `liveParameters`, поэтому `PARAM_LIST` пуст. В headless параметры
    задаются только `--set` при создании. Проверочный скрипт создаёт обе симуляции с одинаковым `--set`, а загрузка в headless
    сверяет `header.params` с ними и предупреждает о расхождении.
16. **Песочница headless** (`vm`): нет `TextEncoder/TextDecoder` и `CompressionStream`. Добавить `TextEncoder, TextDecoder` в `sandbox`
    (headless.cjs:126), а сжатие делать снаружи через `zlib`. Типизированные массивы из другого realm: не проверять `instanceof`,
    копировать через `.set()`.
17. **`JSON` и числа**: NaN, Infinity и −0 теряются (§2). Особенно опасно для mind, где −1 = «нет цели»: такие числа только в бинарных чанках.
18. **Ссылки на объекты**: `_gardens` — ссылки на `biomeSeeds` или `_poolCenter`. При загрузке это новые объекты `{x,y,type}`, используются только как координаты.
19. **Потоки и детерминизм**: проверить, что результат не зависит от числа потоков (если физика читает чужие строки во время записи, порядок плавает).
    Тест §5 сначала в headless (1 поток), потом в браузере с одним и тем же числом потоков.
20. **Версия «+»** (`__GENEPOOL_VERSION__` с `+` — незакоммиченные правки): бит-в-бит не обещать.
21. **Рисование не должно влиять на шаги.** `_rendering` вызывает `rebuildAliveIndexCaches()` между шагами: это безвредно, кэш и так
    перестраивается в начале шага. Проверить, что после замены ГСЧ ничто в рисовании не зовёт `gpRandom`.

## 5. План реализации (для Sonnet), по шагам, коммит после каждого

**Шаг 1. Свой глобальный ГСЧ.** `src/simulation/Globals.ts`: `rngState`, `setRandomSeed`, `getRandomState/setRandomState`,
`gpRandom` = mulberry32 (как `botRandom`). `simhost.worker.ts` init: зерно из `crypto.getRandomValues`, `pool.setSeed(seed)`.
`tools/headless.cjs`: `vm.runInContext("setRandomSeed(" + seed + ")")` после загрузки бандла, `TextEncoder/TextDecoder` в sandbox.
*Проверка:* `node tools/form-census.cjs --seed 1 --steps 3000 --every 1000 --out tools/results/rng-a` до и после правки — `census.csv` совпадают.

**Шаг 2. Доступ к скрытому состоянию** (только чтение и запись, без логики):
- `Disease.ts`: `exportStrains(): Float32Array`, `importStrains(a)`.
- `Environment.ts`: `exportRaw()` → {time, soilNutrient, nutrientUpdatedAt, plantCount0/1}, `importRaw(r)`.
- `Embryology.ts`: `part.origin = p` при генерации.
- `Swimbot.ts`: `getPrivateState(out: Float64Array, at)`, `setPrivateState(src, at)` (§1.2), `getPhenotypeOrigins(out: Int8Array, at)`,
  `restorePhenotypeOrder(origins)` (§4 п.6, затем `processPhenotype`), `setDeathCause(code)`.
- `FamilyTree.ts`: `exportState()`, `importState(s)`.
- `ParamStore.ts`: `changedParams()` → отличия от `PARAM_DEFAULTS`.

**Шаг 3. Упаковщик** `src/simulation/WorldFile.ts` (без DOM, без сжатия): `packWorld(header, chunks[]) → Uint8Array`,
`unpackWorld(bytes) → {header, get(name) → TypedArray}`, `hashChunk(typed) → hex` (FNV-1a 32 по байтам), `layoutFingerprint()`.
Headless подхватит модуль сам: он бандлит все `.ts` из `src/simulation`.

**Шаг 4. GenePool** (`src/simulation/GenePool.ts`, рядом с `getPoolData`): `this.saveWorld(): Uint8Array` (§1, §2) и
`this.loadWorld(bytes): { ok, reason?, needWorld?, mismatches? }` строго по порядку §3. `this.worldHash(): {chunk: hex}` = хеши тех же чанков.

**Шаг 5. Проверочный скрипт** `tools/save-load-check.cjs` (на основе `createSimulation` из headless.cjs):
```
node tools/save-load-check.cjs --seed 1 --warm 3000 --after 2000 --set "…"
```
- **A (сохранение без побочных эффектов):** сим1 делает warm шагов, `saveWorld()`, потом after шагов → хеш A.
  Сим2 (тот же seed) делает warm+after шагов без сохранения → хеш B. Должно быть A == B.
- **B (точное продолжение):** сим3 с **другим** seed проходит 500 «грязных» шагов, затем `loadWorld(файл сим1)` и after шагов → хеш C. Должно быть C == A.
- При расхождении шагать по одному и найти **первый шаг и первый чанк**, где хеши разошлись; для этого чанка вывести слот и поле
  (индекс → `s = i / STRIDE`, `field = i % STRIDE`, имена из SharedState/MindLayout).
- Прогнать на seed 1, 2, 3, в момент с болезнями и автотомией (`--warm 20000`) и при `PLANT_REGROW_CHANCE > 0`.
- Записать размер файла (сырой и gzip) для 2000 и 8000 свимботов.
Прогоны короткие (минуты), см. правило 5 в CLAUDE.md.

**Шаг 6. Поток симуляции** `src/simhost.worker.ts`: сообщения `saveWorld` и `loadWorld` (распаковка `DecompressionStream`,
перенос буфера без копии), ответы `worldSaved`, `worldLoaded`, `worldLoadFailed{reason, needWorld}`. `RemotePool.ts`: `saveWorld(): Promise<Blob>`,
`loadWorld(file)`. RunRecorder: `pool.onWorldLoaded` начинает новую папку `…_loaded-step<clock>`.

**Шаг 7. Интерфейс**: кнопки «Сохранить мир» и «Загрузить мир» в панели бассейна (`index.html`, `src/ui/ui.ts`), тексты и подсказки «?» в `src/ui/lang.ts`
(RU/EN), галочка «с родословной». Если не тот размер мира: файл в IndexedDB → перезагрузка с `?world=N` → автозагрузка.
Если не та раскладка: окно «мягкая загрузка (гены и позиции) / отмена».
*Проверка в браузере (сервер genepool-dev2, порт 5199):* сохранить → загрузить → посмотреть на `worldHash()` в консоли потока
и на то, что график, болезни и течения на месте. Вкладку пользователя не трогать.
